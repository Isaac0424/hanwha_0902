# RAG 파라미터 최적화 방법론

`examples/05_rag_local_docs.py` 기준으로, RAG 파이프라인의 주요 하이퍼파라미터(청크 크기,
임베딩 모델, top-k, 벡터 공간)를 어떻게 고르고 튜닝하는지 정리한 문서.

## 파이프라인 개요

```
문서(.txt) → TextSplitter(chunk_size/overlap) → 임베딩 모델 → 벡터스토어(Chroma)
                                                                    ↓
질문 → 임베딩 모델(동일 모델) → 유사도 검색(top-k) → LLM(qwen3.5:9b) → 답변
```

각 단계의 파라미터가 검색 품질과 최종 답변 품질에 함께 영향을 준다. 하나씩 감으로 바꾸지 말고,
아래 순서로 **평가 → 측정 → 스윕**하는 루프를 돌리는 것이 정석이다.

## 1. `chunk_size` / `chunk_overlap`

| 항목 | 작게(200~400) | 크게(800~1500) |
|---|---|---|
| 검색 정밀도 | 높음 — 관련 부분만 정확히 매칭 | 낮음 — 무관한 내용 섞여 유사도 흐려짐 |
| 문맥 보존 | 낮음 — 문장/문단이 잘릴 수 있음 | 높음 — 앞뒤 맥락 유지 |
| LLM 컨텍스트 비용 | 낮음 | 높음 (긴 컨텍스트 = 느림 + 비쌈) |
| 적합한 질문 유형 | 단답형 사실 질문 | 요약/여러 문단에 걸친 설명 |

**정하는 기준**
- 문서 구조를 최대한 따라간다. `RecursiveCharacterTextSplitter`는 문단→문장→단어 순으로
  재귀 분할해 의미 단위를 최대한 보존하도록 설계돼 있다.
- `chunk_overlap`은 보통 `chunk_size`의 10~20%. 청크 경계에서 문장이 잘려 의미가 끊기는
  것을 완화하는 용도. (`05_rag_local_docs.py`는 200/20 = 10%로, 데모용 짧은 문서에 맞춘 값)
- 실제 문서(매뉴얼, 논문, 사내 위키 등)로 바꾸면 문서당 평균 문단 길이에 맞춰 재조정 필요.

**"연구된 비율"이 있는가?** — 문단 길이 대비 몇 %로 자르라는 식의 검증된 공식은 없다. 다만
참고할 만한 경험적 근거는 있다.

| 출처 | 내용 |
|---|---|
| DPR(Karpukhin et al., 2020) | 위키피디아 QA에서 ~100단어(영어 기준 500~700자) 패시지를 표준으로 사용 |
| Pinecone "Chunking Strategies" 벤치마크 | 256/512/1024 토큰 비교 결과 단일 승자 없음 — 임베딩 모델·질문 유형에 따라 순위가 바뀜 |
| "Lost in the Middle"(Liu et al., 2023) | chunk_size보다 top-k로 넣는 총 컨텍스트 길이가 문제 — 길어질수록 LLM이 중간 정보를 놓치는 경향 확인 |

결론: DPR의 ~100단어 또는 256~512 토큰을 출발점으로 잡고, 5번 평가 루프로 실제 문서에 대해
직접 스윕하는 것이 "정해진 비율을 찾는 것"보다 근거 있는 접근이다.

### 대안: 시맨틱 청킹(semantic chunking)

고정 크기 대신 **문장 간 임베딩 거리가 급격히 벌어지는 지점**(주제 전환 지점)을 경계로 자르는
방식(LangChain `SemanticChunker`, LlamaIndex `SemanticSplitterNodeParser`). 문단 길이가
불규칙한 실제 문서에는 고정 비율보다 원칙적으로 더 맞는 접근.

**약점**: 문서가 같은 주제를 길게 서술하면 거리가 계속 완만해서 경계가 안 생기고, 청크 하나가
지나치게 커질 수 있다. 실무에서는 아래로 보완한다.

- **하드 캡 + 폴백 분할**: 시맨틱 청킹 결과 중 상한(예: 1000자/512토큰)을 넘는 청크만
  `RecursiveCharacterTextSplitter`로 한 번 더 강제 분할. "의미 우선, 크기는 안전장치로 보정"하는
  2단계 구조.
- **`buffer_size` 조절**: 문장을 몇 개씩 묶어 거리를 계산하는 단위. 작을수록 미세한 주제
  변화도 감지해 청크가 잘게 쪼개짐, 클수록 노이즈에 둔감해지지만 큰 청크가 나올 위험 증가.
- **`breakpoint_threshold_type` 조정**: 기본값 `percentile` 대신 `standard_deviation` /
  `gradient`(변화율 기준, 법률·기술 문서처럼 미묘한 전환에 민감)로 바꿔 경계 민감도를 높일 수
  있음. 민감할수록 잘게 쪼개지되 과도한 파편화와 트레이드오프.
- **부모-자식 청킹(Parent Document Retriever)**: 검색은 작은 자식 청크로 정밀하게 하고,
  매칭되면 그 청크가 속한 더 큰 부모 청크(또는 원본 섹션) 전체를 LLM에 넘기는 구조. "청크가
  얼마나 커야 하나"라는 딜레마를 검색용/생성용으로 분리해 우회하는, 가장 깔끔한 해법.

## 2. 임베딩 모델 선택

**공통 원칙**
- 문서 임베딩과 질문 임베딩은 **반드시 같은 모델**을 써야 한다. 모델이 다르면 벡터 공간이
  일치하지 않아 유사도 비교 자체가 무의미해진다.
- 언어/도메인 적합성이 크기(파라미터 수)보다 중요한 경우가 많다. 한국어 비중이 높은
  문서라면 다국어 성능이 검증된 모델을 우선 고려한다.
- 참고 벤치마크: [MTEB(Massive Text Embedding Benchmark)](https://huggingface.co/spaces/mteb/leaderboard)
  리더보드의 Retrieval 태스크 점수. 모델별 실제 순위는 계속 바뀌므로 도입 시점에 다시 확인할 것.

**Ollama에서 받을 수 있는 임베딩 모델 후보** (이름/특성은 도입 시점에
`ollama pull <model>`로 실제 존재 여부를 재확인할 것 — 라이브러리 목록은 계속 갱신됨)

| 모델 | 대략 크기 | 특징 | 이럴 때 |
|---|---|---|---|
| `nomic-embed-text` | ~137M, 768차원 | 가볍고 빠름, VRAM 부담 적음. 현재 프로젝트 기본값 | 로컬 저VRAM 환경, 데모/실습 |
| `mxbai-embed-large` | ~335M | 영어 기준 검색 품질 우수, 중간 크기 | 영어 위주 문서, 품질/속도 절충 |
| `bge-m3` | ~568M | 다국어(한국어 포함) 강함, 긴 컨텍스트(최대 8192 토큰) 지원, dense+sparse 하이브리드 가능 | 한국어 문서, 문서가 길어 청크를 크게 잡고 싶을 때 |
| `snowflake-arctic-embed` | 계열별 상이(22M~335M) | 크기별 라인업 있어 속도/품질 절충 가능 | VRAM 제약이 있는데 nomic보다 품질 올리고 싶을 때 |

RTX 2070 Max-Q(VRAM 8GB)처럼 채팅 모델(`qwen3.5:9b`, ~6.6GB)과 임베딩 모델을 **동시에
상주**시켜야 하는 환경에서는, 임베딩 모델은 가급적 작게(수백MB~1GB대) 유지하는 것이 실질적으로
중요하다.

## 3. `top-k` (검색 개수)

- **너무 작으면(k=1~2)**: 정답이 담긴 청크가 검색에서 누락될 위험 (recall 저하).
- **너무 크면(k=10+)**: 무관한 청크가 섞여 LLM이 혼동하거나("lost in the middle" 현상),
  컨텍스트 길이 낭비.
- **시작점**: k=3~5. `05_rag_local_docs.py`는 k=3.
- **중복 억제가 필요하면 MMR**(Maximal Marginal Relevance)로 유사한 청크끼리 겹치는 것을 줄인다:

  ```python
  retriever = vectorstore.as_retriever(
      search_type="mmr", search_kwargs={"k": 3, "fetch_k": 10}
  )
  ```

## 4. 벡터 공간(유사도 메트릭 / 인덱스)

### L2 거리 vs 코사인 유사도

- **L2(유클리드) 거리**: 두 벡터 사이 직선 거리 `sqrt(Σ(aᵢ-bᵢ)²)`. 작을수록 유사. **벡터의
  크기(magnitude)에 민감**하다는 게 약점 — 방향(의미)이 같아도 벡터 길이가 다르면 거리가
  벌어져서, "크기 차이"와 "진짜 의미 차이"가 섞여버린다.
- **코사인 유사도**: 두 벡터의 **각도**만 비교 (`cos θ = A·B / (‖A‖‖B‖)`), 크기는 무시. 대부분의
  임베딩 모델이 애초에 코사인 기준으로 학습·평가되기 때문에, 검색도 코사인으로 맞춰야 모델
  성능을 제대로 활용할 수 있다.
- **정규화하면 둘은 동치**: 벡터를 단위벡터(L2 norm = 1)로 정규화하면 `‖a-b‖² = 2 - 2·cos(a,b)`
  가 성립해 L2 순위와 코사인 순위가 같아진다. 문제는 정규화하지 않은 벡터를 L2로 검색하면
  모델이 실제로 학습된 기준(코사인)과 어긋난 순위가 나온다는 것. Chroma 기본값이 L2이므로,
  명시적으로 코사인을 지정하는 걸 권장:

  ```python
  vectorstore = Chroma.from_documents(
      docs, embedding=embeddings,
      collection_metadata={"hnsw:space": "cosine"},
  )
  ```

- **내적(Dot Product/IP)**: 정규화된 벡터끼리는 내적 = 코사인 유사도와 동일하며, 정규화
  연산을 생략할 수 있어 더 저렴하다. OpenAI 임베딩, FAISS `IndexFlatIP` 등이 "정규화 후 내적"을
  코사인 대신 쓰는 이유.

### 인덱스(HNSW 등) 파라미터

문서 수가 수만~수백만 개로 커질 때만 유의미. 지금처럼 인메모리·소규모 데이터셋에서는 영향이
거의 없다.

### Chroma 외 다른 벡터 스토어

| 스토어 | 지원 거리 메트릭 | 인덱스 방식 | 특징 |
|---|---|---|---|
| **Chroma** | L2(기본), 코사인, IP | hnswlib(HNSW) | 로컬/인메모리 우선, 설정 간단, 소규모 실습에 적합 |
| **FAISS**(Meta) | L2, IP | Flat(정확), IVF, HNSW, PQ(압축) | 라이브러리(서버 아님), 세밀한 인덱스 튜닝, 대규모(수백만~수억) 벡터에 강함 |
| **Qdrant** | 코사인, 내적, L2 (컬렉션별 선택) | HNSW | 자체 호스팅 프로덕션 벡터 DB, 메타데이터 필터링 강력 |
| **Weaviate** | 코사인, 내적, L2², 맨해튼, 해밍 | HNSW | GraphQL API, 하이브리드 검색(키워드+벡터) 내장 |
| **pgvector**(Postgres 확장) | L2(`<->`), 내적(`<#>`), 코사인(`<=>`) | IVFFlat, HNSW | 이미 Postgres를 쓰면 관계형 데이터와 벡터를 한 DB에서 조인 가능 |
| **Milvus** | L2, IP, 코사인 | IVF, HNSW, DiskANN 등 | 수십억 벡터급 초대규모, 운영 복잡도 높음 |
| **Pinecone** | 코사인, 내적, 유클리드 | 관리형(비공개) | 완전 매니지드 SaaS, 인프라 관리 불필요(로컬/무료 아님) |

이 프로젝트 규모(로컬, 문서 1개)에서는 Chroma나 FAISS로 충분하다. Qdrant/Weaviate/pgvector는
필터링·기존 Postgres 연동 같은 실제 요구가 생겼을 때, Milvus/Pinecone은 데이터가
수백만 건 이상이거나 운영을 위탁하고 싶을 때 고려 대상이 된다.

## 5. 평가 방법론 (핵심 루프)

파라미터를 하나씩 바꿔가며 "느낌"으로 판단하지 않고, 아래 루프를 돌린다.

1. **평가셋 구축**: 질문 20~50개 + 정답(또는 "정답이 들어있어야 할 청크") 쌍을 준비.
2. **검색 품질 지표**
   - `Recall@k`: 정답 청크가 top-k 안에 포함된 비율.
   - `MRR`(Mean Reciprocal Rank): 정답 청크가 몇 번째 순위에 나왔는지의 평균 역수.
3. **답변 품질 지표**: [RAGAS](https://github.com/explodinggecko/ragas) 같은 프레임워크로
   `faithfulness`(환각 여부), `answer_relevancy`, `context_precision`, `context_recall`을
   자동 채점.
4. **그리드 서치**: `chunk_size ∈ {200, 500, 1000}` × `k ∈ {3, 5, 8}` × 임베딩 모델 2~3개
   조합을 돌려 지표를 비교.
5. **선택 기준**: 지표뿐 아니라 로컬 GPU 환경의 VRAM/속도 제약까지 함께 고려해 비용 대비
   성능이 가장 좋은 조합을 채택.

## 요약 체크리스트

- [ ] 문서 구조에 맞는 `chunk_size`/`overlap`인가 (문단이 부자연스럽게 잘리지 않는가)
- [ ] 문서 임베딩과 질문 임베딩에 동일한 모델을 쓰고 있는가
- [ ] 언어/도메인에 맞는 임베딩 모델을 골랐는가 (한국어 비중이 높다면 다국어 모델 검토)
- [ ] `top-k`가 recall과 노이즈 사이에서 적절한가, 중복이 많다면 MMR을 고려했는가
- [ ] 유사도 메트릭을 코사인으로 맞췄는가
- [ ] 평가셋과 지표(Recall@k, MRR, RAGAS 등) 없이 파라미터를 바꾸고 있지는 않은가
